01 THE CLASS

A class is a blueprint. Nothing runs until someone builds from it.

Fields hold state. Methods define behavior. A class by itself never runs — it's the drawing, not the building.

Four definitions to start from

class

A blueprint that defines the fields (state) and methods (behavior) an object of that type will have. A class holds no data of its own — it's a template, not a thing.

object

A specific instance created from a class, with its own independent copy of that class's fields, living on the heap.

field

A variable declared inside a class. Holds one piece of an object's state — each object gets its own copy.

method

A block of code declared inside a class that defines one behavior an object can perform.

Employee.javareal javac + java
public class Employee {
    private String name;
    private double salary;

    public Employee(String name, double salary) {
        this.name = name;
        this.salary = salary;
    }

    public void raiseSalary(double amount) {
        this.salary += amount;
    }

    public void printSlip() {
        System.out.println(name + " earns $" + salary);
    }

    public static void main(String[] args) {
        Employee e1 = new Employee("Asha", 50000);
        Employee e2 = new Employee("Raj", 60000);

        e1.raiseSalary(2000);

        e1.printSlip();
        e2.printSlip();
    }
}

Notice: e1 and e2 are separate objects built from the same blueprint. Raising e1's salary never touches e2 — each object carries its own copy of every field. That's the whole point of a class: define the shape once, stamp out as many independent instances as you need.
02 CREATING AN OBJECT

What actually happens when you write new Employee(...)

Five things happen, in this exact order, every single time. Step through it.

new operator

The keyword that triggers object creation — allocates heap memory for a fresh instance, then hands off to its constructor.

constructor

A special method sharing the class's name, with no return type. Finishes setting up a new object — always the last step in creation, never the first.

The order never changes: allocate on the heap with defaults (null / 0 / false) → run field initializers → run the constructor body → hand back a reference. The constructor is the last step, not the first — it finishes an object that already exists in memory, it doesn't create it from nothing.
03 THE FULL LIFECYCLE

Static blocks, instance blocks, field initializers, constructors — who runs when?

Four terms that get thrown around loosely. Let's define each one precisely before we watch them run in order.

Four definitions, once each

static block

static { ... } written directly in the class body. Runs exactly once — the moment the class is first loaded by the JVM, before any object of that class exists.

instance initializer block

{ ... } with no keyword, written directly in the class body. Runs every time an object is created — after field initializers, before the constructor body.

field initializer

The = value part of a field declaration, e.g. int seat = 42;. Runs every time an object is created, in the order the fields are written.

constructor

A method sharing the class's name, no return type. Runs every time an object is created — and always runs last, after everything above has already happened.

The complete object lifecycle, start to finish
1
Once per class

Class is loaded

The JVM loads the class the first time it's actually needed. Static fields get their defaults, then static field initializers and static blocks run, top to bottom, in source order.

2

new Ticket(...) is called

The JVM allocates a fresh block of memory on the heap. Every field starts at its default: null, 0, or false — nothing is "set" yet.

3
Every single object

Field initializers & instance blocks run

In the exact order they're written in the class, top to bottom — interleaved if you mix them.

4
Every single object

Constructor body runs

The last step of construction, not the first. This is where constructor parameters actually get used.

5
Ongoing

Object is live and reachable

A reference to it exists somewhere reachable — a stack variable, a static field, or inside another reachable object. Methods can be invoked on it. (Sheet 02's JVM Memory Map section covers stack and heap in depth.)

6

Last reference is dropped

Nothing reachable from any GC root points to it anymore. It is now eligible for garbage collection — not collected yet, just eligible.

7

The JVM reclaims the memory at a time entirely of its own choosing. See "How It's Freed" for exactly what that means and why.

04 THIS & METHOD INVOCATION

A method doesn't run in a vacuum — it runs in the context of one object

a.increment() is really "run increment() with this bound to a." Two objects, same method, two separate outcomes.

this

A hidden reference every non-static method receives automatically — points at the exact object the method is currently running on.

method invocation

Calling a method on a specific object. The method's code runs once, using that particular object's own field values — not any other object's.

Counter.javareal javac + java
public class Counter {
    private int count = 0;
    public void increment() { this.count++; }
    public int getCount() { return count; }

    public static void main(String[] args) {
        Counter a = new Counter();
        Counter b = new Counter();
        a.increment();
        a.increment();
        b.increment();
        System.out.println("a=" + a.getCount() + " b=" + b.getCount());
    }
}
STDOUT — java Counterexit 0
a=2 b=1

What "this" is really doing

this is a hidden reference every non-static method secretly receives — it's how count++ knows whose count field to touch.

Conceptually, the compiler treats a.increment() almost like a static call: Counter.increment(a). That's why a and b never interfere — they're just two different first arguments.

This is also why static methods can't use this — there's no object bound to them at all.

05 ACCESS SPECIFIERS

Four clearance levels for who can touch a field or method

Not a syntax rule to memorize — a safety mechanism. The tighter the circle, the fewer places can break when you change what's inside it.

access specifier

A keyword (public, protected, default, or private) that controls which parts of a program are allowed to see or use a field or method.

encapsulation

Keeping a class's internal data private and exposing only controlled access through its methods — the design goal access specifiers exist to serve.

A top-level class can only ever be public or (default) — never private, never protected. Those two only make sense once something can contain the class — fields and methods live inside a class, but a top-level class isn't inside anything. (A nested class, declared inside another class, can be private — that's different.)

06 HOW IT'S FREED

An object becomes garbage the instant nothing can reach it

Not when you're "done with it." Not when a scope ends. The exact moment no reference chain from a GC root leads to it anymore.

garbage collection (GC)

The JVM's automatic process of finding and reclaiming the memory used by objects that nothing can reach anymore.

reachability

Whether an object can still be reached by following references starting from an active stack variable, a static field, or another reachable object.

GcDemo.javareal javac + java
import java.lang.ref.WeakReference;

public class GcDemo {
    public static void main(String[] args) throws InterruptedException {
        Object obj = new Object();
        WeakReference<Object> ref = new WeakReference<>(obj);

        System.out.println("Before: reachable = " + (ref.get() != null));
        obj = null; // drop the only strong reference
        System.gc(); // just a request, not a guarantee
        Thread.sleep(200);
        System.out.println("After:  reachable = " + (ref.get() != null));
    }
}

Important honesty check: System.gc() is only a request — the JVM is free to ignore it. You can never reliably predict or force exactly when garbage collection happens in production, and you should never write logic that depends on it happening at a specific time. That's a deliberate design choice, not a gap.
One more piece of history worth knowing: Object has always had a finalize() method — a hook the garbage collector was supposed to call right before reclaiming an object, so it could clean up after itself. In practice it was unreliable (no guarantee it would ever run, or when) and became a genuine source of production bugs. It's been deprecated since Java 9. The modern replacement is exactly what the "Best Practices" section already tells you: try-with-resources and AutoCloseable for anything that truly must be cleaned up — don't lean on the collector to do it for you.

Eleven methods — what they do, and when to reach for them

isNull(obj)

What: true if obj is null.

Why / when: reads more naturally than obj == null as a method reference — mainly useful as Predicate, e.g. list.stream().filter(Objects::isNull) to find the nulls in a collection.

nonNull(obj)

What: true if obj is NOT null — the opposite of isNull.

Why / when: the far more common one in practice — list.stream().filter(Objects::nonNull) to strip nulls out of a stream before processing it further.

requireNonNull(obj, msg)

What: returns obj if present; throws NullPointerException(msg) immediately if not.

Why / when: validating constructor arguments and method parameters up front — the standard "fail fast" pattern, so a null is caught right where it entered instead of causing a confusing NPE three calls later.

requireNonNullElse(obj, def)

What: returns obj if present, otherwise a fallback default — no exception at all.

Why / when: optional configuration, or a parameter that's allowed to be null and just needs a sensible default — replaces obj != null ? obj : default written out by hand.

requireNonNullElseGet(obj, supplier)

What: like requireNonNullElse, but the default is computed lazily by a Supplier — only called if obj really is null.

Why / when: when the fallback value is expensive to build (a database lookup, a new object) and you don't want to pay for it on the common, non-null path.

equals(a, b)

What: null-safe equals — true if both null, false if only one is, .equals() otherwise.

Why / when: comparing two values where either might be null — most commonly inside a class's own equals() override, where a field itself could legally be null.

deepEquals(a, b)

What: like equals(), but compares array CONTENTS (recursively, for nested arrays too) instead of array identity.

Why / when: exactly the same job as Arrays.deepEquals() from Sheet 02, but null-safe on the arrays themselves — reach for it when either array reference might be null.

hashCode(obj)

What: obj.hashCode(), or 0 if obj is null — never throws.

Why / when: the companion to Objects.equals() above — inside a hashCode() override, for any single field that might be null.

hash(a, b, c, ...)

What: combines several values into one hash code.

Why / when: the standard, one-line way to implement hashCode() across multiple fields — instead of hand-writing the classic "multiply by 31 and add" boilerplate yourself.

toString(obj, def)

What: obj.toString(), or a fallback string if obj is null.

Why / when: building log messages or user-facing output — turns a null into a controlled placeholder like "N/A" instead of the literal text "null" leaking into a message.

compare(a, b, comparator)

What: 0 if a and b are the same reference (including both null); otherwise delegates to the given Comparator.

Why / when: writing a custom Comparator for sorting, when you want the "same object" and "both null" cases handled for free instead of special-casing them yourself.

Why this beats hand-rolled null checks: Objects.equals(a, b) replaces a != null && a.equals(b) everywhere in a codebase, correctly, every time. It's the same instinct as everything else in this checklist — push a repeated, easy-to-get-wrong pattern into one well-tested method instead of retyping it.

01 JVM MEMORY MAP

One JVM process. Several very different kinds of memory.

Sheet 01 covered stack and heap for a single object. Here's the whole picture — every area a running JVM actually divides its memory into.

Four definitions before the map

JVM

The Java Virtual Machine — the running process that actually executes compiled Java bytecode, managing memory, threads, and class loading for the program.

heap

One shared region of memory per JVM, reachable by every thread, where every object created with new lives. Managed by the garbage collector.

metaspace

Native memory holding class metadata — bytecode, method information, and runtime class details. Static fields are associated with the class, but in modern JVMs (Java 8+) their actual values live on the heap, alongside the Class object itself — not in Metaspace.

stack

A region of memory private to one thread, holding that thread's local variables and method call frames. Grows and shrinks automatically as methods are called and return.

Heap — one per JVM, shared by every thread

Every object you create with new lives here. Garbage collected. Divided internally so the collector can work efficiently:

Young Generation
Eden + two Survivor spaces. Nearly all objects are born here — and most die here too, fast.
Old Generation
Objects that survive several collections get "promoted" here. Collected far less often.

The String Pool (Sheet 02, Section 02) has lived inside the heap since Java 7 — before that it was a fixed-size area of its own.

Metaspace — one per JVM, native memory

Holds class metadata — bytecode, method information, the runtime constant pool, and runtime class details.

Static fields are associated with the class, but in modern JVMs (Java 8+) their actual values live on the heap alongside the Class object — not as slots in Metaspace.

Metaspace itself is native memory, not the heap. It grows dynamically by default (unlike its predecessor, PermGen, which had a fixed size and was a notorious source of OutOfMemoryError before Java 8).

Stack — one per thread, private to that thread

Every thread gets its own stack the moment it starts, holding that thread's own call frames. No thread can see another thread's stack.

02 STRING POOL & INTERNING

Some strings are shared on purpose. Some aren't.

Predict all three before revealing — this is the single most common source of a "why doesn't == work on strings?" bug report.

string pool

A dedicated area inside the heap where the JVM keeps exactly one shared copy of every String literal, so identical literals reuse the same object instead of duplicating it.

interning

The act of looking up (or adding) a string's shared copy in the pool — happens automatically for literals, or manually via .intern().

StringPoolDemo.javareal javac + java
public class StringPoolDemo {
    public static void main(String[] args) {
        String a = "hello";
        String b = "hello";
        String c = new String("hello");
        String d = c.intern();

        System.out.println("a == b: " + (a == b));
        System.out.println("a == c: " + (a == c));
        System.out.println("a == d: " + (a == d));
    }
}
STDOUT — java StringPoolDemoexit 0
a == b: true
a == c: false
a == d: true
What's actually happening: string literals ("hello" written directly in code) are automatically interned — the JVM keeps exactly one shared copy in the string pool (which lives inside the heap). a and b are two variables pointing at that same shared copy, so == is true. new String("hello") deliberately bypasses the pool and allocates a fresh, separate object — same characters, different box, so == is false. Calling .intern() manually looks up (or adds) the pool's copy and hands it back, which is why d matches a again.
The rule this leads to: never compare String content with ==. Always .equals(). Strings that arrive from user input, a file, a network call, or new String(...) are never guaranteed to be the pooled instance, even if the characters are identical.
03 MEMORY LEAKS

Java has a garbage collector. It still leaks memory constantly in production.

The GC only reclaims objects nothing can reach. It says nothing about objects your own code is still, technically, holding onto.

memory leak (in Java)

Memory that's still reachable — so the garbage collector can't touch it — but that the program will never actually use again. Not a JVM bug; a design or logic issue in the code holding the reference.

LeakDemo.javareal javac + java
import java.util.*;

public class LeakDemo {
    static List<byte[]> cache = new ArrayList<>(); // static -- lives for the whole program

    static void handleRequest() {
        cache.add(new byte[1_000_000]); // 1MB, added but never removed
    }

    public static void main(String[] args) {
        for (int i = 0; i < 5; i++) {
            handleRequest();
            System.out.println("request " + i + " handled, cache now holds: " + cache.size() + " entries");

This will never throw an exception here, and the GC will never touch that array data. Every one of those 1MB arrays is still reachable — through cache, a static field, which lives for the entire life of the program. Run this for 5 requests and it looks harmless. The usual suspects, in real production code

  • ✓
    Static collections that only ever grow.A cache, a registry, a "seen IDs" set — anything static that accumulates and is never trimmed or bounded.
  • ✓
    Listeners and callbacks that are registered but never unregistered.An object adds itself as a listener to something long-lived; nobody ever calls removeListener. The long-lived object now keeps the short-lived one alive forever.
  • ✓
    Inner (non-static) classes holding a hidden reference to their outer instance.Every non-static inner/anonymous class instance secretly holds a reference back to the object that created it — which can keep that whole outer object alive longer than intended.
  • ✓
    ThreadLocal values that are set but never removed.Especially dangerous in thread-pooled servers, where the same thread — and its ThreadLocal storage — is reused for years.

Best practices to avoid them

  • ✓
    Bound every cache with a max size and an eviction policy.An access-ordered LinkedHashMap (Sheet 01's LRU pattern), or a real caching library — never a plain collection that only ever grows.
  • ✓
    Always pair register with unregister.Ideally in a try/finally. Where that's impractical, use WeakHashMap or WeakReference for the registry itself, so entries can be collected even if you forget to remove them.
  • ✓
    Prefer static nested classes over non-static inner classes.Unless you genuinely need the outer instance — a non-static inner class silently holds a reference back to it forever, whether you use that reference or not.
  • ✓
    Call ThreadLocal.remove() when a thread is done with a value.Especially in thread-pooled environments — the thread outlives the request, so its ThreadLocal storage does too, unless you clear it yourself.
  • ✓
    Use try-with-resources for anything Closeable.Files, connections, streams — so cleanup happens even when an exception is thrown partway through.
  • ✓
    Heap-profile long-running services periodically.A slow leak is invisible day to day, but a growing heap trend shows up in a profiler (VisualVM, async-profiler) weeks before it becomes a 3 a.m. OutOfMemoryError.

What "fixed size" really means

new int[3] reserves exactly 3 slots, forever. There's no array.add() — that's what ArrayList is for, and it works by creating a new, bigger array under the hood and copying everything over whenever it runs out of room.

05 METHOD VISIBILITY & POLYMORPHISM

The same line of code, running three different ways

The caller never checks which class it's dealing with. The JVM figures that out at runtime, every time.

method overriding

A subclass providing its own implementation of a method that's already defined in its superclass, using the exact same name and parameters. Marked with @Override by convention.

polymorphism

Calling the same method on different objects and getting each object's own behavior — the caller writes one line of code that behaves differently depending on the actual object.

dynamic dispatch

The mechanism that makes it happen: the JVM looks at the object's ACTUAL class at runtime (not the reference's declared type) to decide which overridden method body to run.

upcasting

Treating a subclass object as its superclass type — Employee e = new Manager();. Always safe, and often implicit — no cast keyword needed.

One more rule worth knowing: a static method on an interface belongs to the interface itself — it is never inherited or overridden by an implementing class, only called as InterfaceName.method().

09 RETURN & ARGUMENT BEHAVIOUR

Which overload actually runs, and what a subclass can promise back

Same method name, five calls, five different bodies picked automatically at compile time.

return / argument behaviour

An object passed as an argument, or handed back as a return value, never loses its real type. Whatever method you call on it afterward still dispatches to the ACTUAL object's version — the declared parameter or return type only affects which method names are visible, exactly like Section 05.

method overloading

Multiple methods sharing a name but differing in parameter types. The compiler picks the best match at compile time — this is NOT the same mechanism as overriding (Section 05), which is resolved at runtime.

varargs

Four questions. No peeking at the answer first.

1. Employee e1 = new Employee(); Employee e2 = e1; — how many Employee objects exist on the heap?

collection

02 MAIN COLLECTION INTERFACES

Five interfaces, five different promises about order, duplicates, and access

Every implementation you'll ever use (Section 03 onward) is just one concrete way of keeping one of these promises.

List

An ordered collection that allows duplicates, accessed by index — "the 3rd element" is always a meaningful question.

Set

A collection that guarantees no duplicates — adding an element that's already present (per equals()) is silently a no-op.

Queue

A collection designed for holding elements before processing, typically first-in-first-out (FIFO) — think of a line of customers.

Deque

"Double-ended queue" — elements can be added or removed from BOTH ends, so it can act as a queue (FIFO) or a stack (LIFO).

Why isn't Map part of Collection?

A Collection's core contract is built around holding individual elements — you add(element) one thing at a time. A Map doesn't hold elements — it holds key-value pairs, and you look things up by key, not by iterating "the next element." Trying to force Map into the same interface as List/Set/Queue would mean add() taking two arguments instead of one everywhere else — a fundamentally different shape. So Map is deliberately its own separate interface hierarchy, even though it lives right alongside the rest of the framework.

03 LIST IMPLEMENTATIONS

Two Lists, one real performance trade-off

Same interface, opposite internal structure — and it shows up immediately once you measure it.

ArrayList

Backed by a resizable array. Random access by index is direct (array math); inserting in the middle means shifting every element after it.

LinkedList

A doubly-linked chain of nodes, each holding a value plus pointers to the previous and next node. No shifting on insert — just relinking two pointers.

07 HOW HASHMAP ACTUALLY WORKS

O(1) lookup isn't magic — it's an array of buckets and a good hash function

The single most important internal-mechanics section in this whole sheet.

hashing

Converting a key into an integer (its hash code) that decides which "bucket" it belongs in — done once per key, cheaply.

bucket

One slot in the HashMap's internal array. Every key with the same computed bucket index lands in the same bucket.

hash collision

Two different keys landing in the same bucket. Not a bug — an expected, handled event, not a failure.

load factor

How full the table is allowed to get (default 0.75, i.e. 75%) before it automatically grows.

Put and get, traced through the buckets

put("Asha", 28)  →  hashCode("Asha") = -1234  →  bucket index = hash & (capacity-1)  →  bucket 5

Internal array (capacity 16):
 [0] [1] [2] [3] [4] [5]────► ("Asha", 28)
 [6] [7] [8] [9] ...

get("Asha")  →  same hash  →  same bucket 5  →  found immediately, no scanning the whole table

Collision case -- "Asha" and "Bilal" both hash to bucket 5:
 [5]────► ("Asha", 28) ──► ("Bilal", 34)   (a short chain, or a mini tree if the chain gets long)

This is the entire trick behind "O(1) average lookup": instead of scanning every entry, the hash tells you almost exactly which tiny bucket to check. A collision just means checking a couple of entries in that one bucket via equals() instead of exactly one — still nowhere close to scanning everything.

09 COMPARABLE VS COMPARATOR

One sorting rule baked into the class. Unlimited others supplied from outside.

Same three employees, sorted three different ways, using two different mechanisms.

Comparable<T>

Implemented BY the class itself, via compareTo() — defines that type's single "natural order." A class can only have one.

Comparator<T>

A separate object implementing compare(a, b), supplied from outside the class — as many different orderings as you want, without touching the class itself.

ComparableVsComparator.javareal javac + java
class Employee implements Comparable<Employee> {
    String name; int salary;
    Employee(String name, int salary) { this.name = name; this.salary = salary; }

    @Override
    public int compareTo(Employee other) {
        return Integer.compare(this.salary, other.salary); // natural order: by salary
    }
    public String toString() { return name + "(" + salary + ")"; }
}

List<Employee> employees = new ArrayList<>(List.of(
    new Employee("Raj", 60000), new Employee("Asha", 85000), new Employee("Bilal", 45000)));

System.out.println("Natural order (by salary): " + employees);

employees.sort(Comparator.comparing(e -> e.name)); // custom order

Catching a type mistake at compile time instead of at 2am in production

Before Java 5, every collection held plain Object — and the compiler had no way to stop you from mixing types in one.

generics

Wildcards and PECS

The rule that decides whether you're allowed to add() to a wildcard-typed collection.

<? extends T>

"Some subtype of T, I just don't know which." Safe to READ as T. Not safe to add to — the compiler can't guarantee what specific subtype it really is.

<? super T>

"T or some supertype of T." Safe to WRITE a T into. Reading only gives you back a plain Object, since it could be any supertype.

11 AUTOBOXING & UNBOXING

Every collection secretly runs on wrapper objects, not primitives

Generics can't hold an int — only an Integer. That single fact explains a very strange, very real bug.

wrapper class

An object wrapping a primitive value — Integer for int, Double for double, and so on. Needed because generics (Section 10) only work with reference types, never primitives.

autoboxing / unboxing

The compiler automatically converting int ↔ Integer for you — List<Integer> l; l.add(5); silently becomes l.add(Integer.valueOf(5)).

AutoboxingCache.javareal javac + java

Integer c = 200;

System.out.println("Using .equals() instead: " + c.equals(d));
STDOUT — java AutoboxingCacheexit 0
127 == 127 (boxed): true
200 == 200 (boxed): false
Using .equals() instead: true
This isn't a trick question — it's a real, documented JVM behavior. Java caches boxed Integer objects for the range -128 to 127 (small, commonly used values), reusing the same object every time one falls in that range — so == happens to work by coincidence. Step outside that range and each autoboxing creates a genuinely new object, and == correctly reports them as different. The actual rule, always: compare wrapper objects with .equals(), never == — exactly the same String-pool lesson from Sheet 02, now for numbers.

Performance implications

Every autobox/unbox is real work — allocating an object (or hitting the cache) instead of just using a raw value on the stack. A tight loop doing arithmetic on a List<Integer> is measurably slower than the same loop over an int[], because every single access boxes or unboxes. For hot numeric loops, prefer primitive arrays; reach for wrapper-based collections when you need the collection's behavior (uniqueness, ordering, generics) and the performance cost is genuinely negligible for the size of data involved — which is true for the vast majority of everyday code.

13 IMMUTABLE COLLECTIONS

"Unmodifiable" and "immutable" sound the same. They aren't.

One genuinely can't change. The other just can't be changed through that one particular reference.

List.of() / Set.of() / Map.of()

Java 9+ factory methods producing a genuinely immutable collection — no path exists to mutate it, ever, by anyone.

Collections.unmodifiableList(list)

A VIEW wrapping an existing, still-mutable list. The view itself rejects direct changes — but the original list underneath can still be mutated, and that change shows up through the view too.

17 QUICK CHECK

Five questions. No peeking at the answer first.

1. Why is Map not part of the Collection interface?

Correct: Collection's contract is built around single elements. Map fundamentally deals in pairs, so it's deliberately a separate interface hierarchy.

2. A class is used as a HashSet element but only overrides equals(), not hashCode(). What happens?

Correct: HashSet checks hashCode() first to find a bucket, then equals() within it. If hashCode() isn't overridden, two "equal" objects can land in different buckets and never even get compared.

3. What does List<? extends Number> let you safely do?

Correct: this is the "Producer Extends" half of PECS — safe to read as Number, but the compiler can't guarantee what specific subtype it actually is, so writes are blocked.

4. Why does modifying a List directly during a for-each loop throw ConcurrentModificationException?

Correct: for-each is syntax sugar for an Iterator loop. The iterator tracks a modification count and detects the mismatch on its next step, throwing rather than risking silently wrong behavior.

5. Integer a = 100; Integer b = 100; a == b returns true. Integer c = 200; Integer d = 200; c == d returns false. Why?

Correct: the Integer cache is real, documented JVM behavior. It's exactly why wrapper types should always be compared with .equals(), never ==.

01 WHAT ARE STREAMS?

A pipeline that describes what to do with data, not how to loop over it

Same result as a for-loop. A completely different way of expressing the intent.

Stream

A sequence of elements supporting a pipeline of operations (filter, transform, reduce) — introduced in Java 8. A Stream is not a data structure and doesn't store anything; it's a description of a computation over some source of data (a List, an array, a file, and so on).

Why Streams were introduced

Before Java 8, "filter this list, transform what's left, and collect a result" meant writing a loop, an if-check, a new list to collect into, and manually adding to it — every single time, in every project. Streams let you say what you want done, as a chain of small, named steps, and let the JVM handle the looping. It's the same shift Sheet 04 already showed happening at the collection level — Streams push that one step further, into how you process the data, not just how you store it.

03 INTERMEDIATE OPERATIONS & LAZINESS

A pipeline you build does genuinely nothing — until you ask it for an answer

Predict what prints, and when, before revealing.

intermediate operation

An operation that returns another Stream, so more operations can chain after it — filter, map, sorted, distinct, limit, skip. None of them do any actual work by themselves.

Intermediate operations only describe what SHOULD happen. Nothing actually runs until a terminal operation (Section 04) is called — and if one never is, the whole pipeline silently never executes.

08 QUICK CHECK

Three questions. No peeking at the answer first.

1. You build a Stream pipeline with filter() and map() but never call a terminal operation. What happens?

Correct: Streams are lazy. Intermediate operations only describe work — nothing runs until a terminal operation triggers the whole pipeline.

2. A Stream has .count() called on it, then .count() is called on the exact same Stream object again. What happens?

Correct: a Stream is single-use. Once a terminal operation runs, that Stream object is permanently spent — verified with the real exception in Section 05.

3. In a five-element pipeline with filter() then map(), what actually happens internally?

Correct: Section 03's LazinessDemo proved this directly — the real printed order was filter, filter, map, filter, filter, map, filter, not five filters followed by two maps.
